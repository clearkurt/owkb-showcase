# 知识模型

> 本文件描述 OWKB 的内容组织方式，不包含具体项目资料。

## 1. 文档基本结构

```markdown
---
id: example-doc
title: 示例文档
type: doc
collection: 示例/集合
tags: [示例, 文档]
status: published
updated: '2026-01-01'
source: 来源说明
source_code: 代码库/示例项目
---

# 示例文档

正文……
```

必填元数据建议：

| 字段 | 作用 |
|---|---|
| `id` | 稳定标识，移动路径时尽量保持不变 |
| `title` | 人类可读标题，也是检索权重的一部分 |
| `type` | `doc` / `manual` / `code` / `data` 等 |
| `collection` | 集合路径，用于目录与权限分组 |
| `tags` | 关键词，便于筛选与检索 |
| `status` | 发布状态 |
| `updated` | 最后更新时间 |
| `source` | 原始来源，便于追溯 |
| `source_code` | 对应代码镜像路径（如有） |

## 2. 内容类型

### 芯片手册

建议每个手册一个目录：

```text
芯片手册/厂商/型号/
  full.md
  snapshots/
    p012_s1_table.png
    p018_s1_image.png
```

`full.md` 使用页锚点：

```markdown
<!-- pdf-page: 12 -->

## 4.3 定时器

……
```

图片使用相对路径引用，便于离线阅读和跨环境迁移。

### 写法/协议笔记

按主题组织，而不是按时间堆放。每篇尽量包含：

- 结论与适用范围；
- 关键参数/时序/寄存器；
- 可复核的源码或手册依据；
- 已知限制与未决项；
- 可复用片段和验证方法。

### 项目案例

每个项目建议至少包含：

- 项目定位与硬件/软件边界；
- 系统架构与启动流程；
- 功能模块与数据流；
- 硬件绑定、引脚和配置；
- 关键问题、风险和验证记录；
- 源码证据索引。

### 代码库

只收录经批准的源码，按项目分目录，保持原始字节或明确标注转码策略。
代码镜像不参与内容创作，只作为证据和参考。

## 3. 路径与别名

文档移动时保留旧路径别名，避免已有引用失效。
手册、项目案例和代码库各自使用稳定目录约定。

## 4. 页锚点与图片

手册页锚点用于把检索结果定位回 PDF 页；图片快照用于保留表格、框图、
时序图等 Markdown 难以完整表达的内容。

图片引用必须使用相对路径，并在导入时验证文件存在。

## 5. 证据分级

建议在技术文档中区分：

- **源码/手册事实**：可直接复核；
- **推断**：由代码或资料推导，尚未实测；
- **待确认**：缺少手册、硬件或实测证据。

这种标记比“看起来像结论”的文字更有长期价值。

## 6. 质量检查

导入后至少检查：

- frontmatter 完整且可解析；
- 文档 id 唯一；
- 图片/页锚点引用可解析；
- 没有孤儿文档或重复内容；
- 代码镜像与来源一致；
- 没有敏感文件或凭据。
